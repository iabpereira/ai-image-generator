# AI Image Generator

A web app that turns text prompts into images. Users sign up, describe what they want, see the price before generating, and keep a history of everything they created.

Images are generated by the [Pixelforge](https://pixelforge.promptedit.dev/docs) API. The app resells each generation at Pixelforge's cost plus a markup, and records the exact amount once the generation completes.

**Live:** https://ai-image.back-office.cc

## Features

- **Dashboard:** a table of every generation with live status and the actual amount charged.
- **Generate:** its own page, with prompt, size, quality and optional reference images, plus the live cost estimate and your balance.
- **Gallery:** the finished images. Open one in a modal and use the Download button.
- **Credits:** your balance, fake $1, $5 and $20 packs, and a statement. New users land on Credits after verifying their email.
- **Fair pricing:** you pay Pixelforge's actual cost plus the markup (25% by default). Failed generations are free, and the same generation is never charged twice.
- **Private images:** only their owner can see them.
- **Admin (operators only):**
    - The spend report: credit spend, provider cost and profit per UTC day and per user, with a daily check against `/v1/usage`.
    - The user list, with impersonation (a banner and a "Back to my account" button).
    - The editable markup, with its change history.
- **Webhooks:** signed Pixelforge events, verified and processed idempotently, so duplicate or out-of-order deliveries still end in the right state.
- **Accounts:** sign up with email verification, two-factor authentication and profile settings.

> Status: Phase 1 (generation, pricing, history and webhooks) and Phase 2 (credit balances and the admin report) are both live. It was verified in production against Pixelforge's test keywords (`[succeed]`, `[fail]`, `[blocked]`, `[overloaded]`, `[duplicate]`, `[slow]`, plus a burst of 4), and provider costs match `/v1/usage` to the nanodollar.

## How money is handled

Pixelforge reports money as exact decimal strings with 9 places (`"0.046125000"`). The app never uses floats for money: amounts are stored as integer nanodollars and wrapped in a `Money` value object. Each generation keeps the estimate shown to the user and, after it succeeds, the actual provider cost and the amount charged.

## Design decisions

### Money in nanodollars

Money is stored as integer nanodollars (1 USD = 10^9), because Pixelforge reports exact 9-decimal amounts and floats drift. The actual cost is usage tokens times the `rates` stored on that generation (fixed when Pixelforge created it), never the current price list. Code: `app/Support/Money.php`, `app/Services/Pixelforge/CostCalculator.php`.

### Markup and rounding

The charge is the provider cost times 125/100, rounded up to the next nanodollar, so we never undercharge by a fraction. The UI shows 4 decimals. The exact 9-decimal value is in a tooltip.

### Estimate vs. actual charge

Before submitting, the user sees a typical estimate (nominal text tokens, mid-range reasoning) and a maximum (+15% text tokens, max reasoning). The final charge is always the real token cost plus markup. It is deliberately not capped at the estimate: a cap would make our numbers disagree with Pixelforge's `/v1/usage`, and the docs guarantee real usage stays within the range the maximum uses.

### One place changes status and money

`GenerationLifecycle` (`app/Services/Generations/GenerationLifecycle.php`) applies every update, whether it comes from the POST response, a webhook or polling. Each update is a compare-and-set (`UPDATE ... WHERE status IN (allowed previous statuses)`). Duplicate or out-of-order events match zero rows, so a generation never moves backwards and is charged at most once, even when two deliveries race.

### Idempotent submission

The local row is created before calling Pixelforge. Its UUID is sent both as the `Idempotency-Key` and as `metadata.generation_uuid`, so retries never create a second generation and a webhook that arrives before the POST returns still finds its row. The `SubmitGeneration` job waits locally when 3 generations are in flight, honours `Retry-After` on 429, backs off exponentially on 503 and connection errors (5 attempts max), and fails immediately (free) on content policy, validation or daily limit. If a submission we gave up on later turns out to exist at Pixelforge, Pixelforge's state wins.

### Webhooks

The signature is HMAC-SHA256 over `timestamp.raw body`, checked with a constant-time compare and a 5-minute tolerance. The route is outside the web middleware group (no session or CSRF). Events are stored with a unique `event_id` (duplicates are counted, not re-applied) and processed in a queued job, so the endpoint answers within Pixelforge's 10 s.

### Lost webhooks

`generations:sync` runs every minute and polls generations stuck in queued or processing for over 90 s. A 404 from Pixelforge fails the generation (free).

### Images

Pixelforge URLs expire after 24 h, so each finished image is downloaded to our storage. Files are kept on the private disk and served by an owner-only route. Anyone else gets a 404. The response sends `Cache-Control: private`, and `?download=1` returns an attachment.

### Credit ledger

The ledger is append-only, and `users.credit_balance` caches the sum. Submitting holds the maximum possible charge. Success releases the hold and charges the actual price. Failure (including rejected submissions) only releases the hold. A unique `(generation_id, type)` index makes each step happen at most once, on top of the lifecycle's compare-and-set. A generation is refused when the balance can't cover the maximum. Code: `app/Services/Credits/CreditLedger.php`.

### Editable markup

The markup is stored in basis points (2500 = 25%), so fractional markups need no floats. Every change is recorded with the new and previous value, who changed it and when, and the latest change is in force. Each generation fixes the markup in force when it's created and is charged with it, so a change never alters what a user was quoted. A test covers a change made mid-flight.

### Admin report reconciliation

Generations are grouped by the UTC day they completed, because that is how Pixelforge bills. Each day's provider cost is compared with `/v1/usage` for the production API key (usage is reported per key). If `/v1/usage` is down, our numbers are still shown, with a warning.

### Admin access and impersonation

Admin is a `users.is_admin` flag, granted only from the CLI (`php artisan users:promote {email}`). There is no UI to grant admin. Admins can impersonate regular users, never other admins or themselves. The real admin id is kept in the session, and the session id is regenerated on every switch. Switching back signs out completely if that account is no longer an admin.

### One container

The 1 GB host runs a single container: FrankenPHP plus `queue:work` plus `schedule:work` (`docker/start.sh`), SQLite in WAL mode with IMMEDIATE transactions, and a database queue and cache. No Redis or MySQL.

## Stack

- Laravel 13 (PHP 8.5) with Fortify for authentication
- Inertia v3 + Vue 3 + TypeScript, Tailwind CSS 4 and shadcn-vue components
- SQLite, with database-backed sessions, cache and queue
- Pest for tests, Pint, Larastan and Vite+ (oxlint/oxfmt) for code quality
- FrankenPHP in Docker for production, behind Traefik

## Running locally

Requirements: PHP 8.5, Composer and Node 22+.

```bash
composer setup   # install dependencies, create .env, generate the key, migrate, build assets
composer dev     # app server, queue worker, logs and Vite
```

Then set the Pixelforge credentials in `.env`:

```dotenv
PIXELFORGE_API_KEY=
PIXELFORGE_WEBHOOK_SECRET=
PIXELFORGE_MARKUP_PERCENT=25
```

Run the checks the CI runs:

```bash
composer ci:check   # lint, formatting, type checks and the test suite
```

## Deployment

The production server is small (1 GB of RAM), so nothing is built there. `deploy.sh` builds a `linux/amd64` image locally with Podman (or Docker) and ships only what's needed to run it:

```bash
./deploy.sh
```

1. **Build:** a multi-stage build runs `composer install --no-dev` and `npm run build`. The final FrankenPHP image contains only `vendor/`, the compiled assets and the PHP code.
2. **Ship:** the image is streamed to the server over SSH (`docker save | gzip | ssh … docker load`).
3. **Start:** `docker compose up -d` starts the container. On start it runs migrations and caches config, routes, views and events.

On the server, `~/apps/ai-image-generator` holds only:

| File                 | Purpose                                                                                               |
| -------------------- | ----------------------------------------------------------------------------------------------------- |
| `docker-compose.yml` | The service, its Traefik labels and the volumes for the SQLite database and uploads                   |
| `deploy.env`         | Domain and Traefik settings (see `deploy.env.example`)                                                |
| `.env.production`    | Laravel settings and secrets (see `.env.production.example`); never committed or baked into the image |

Email (verification and password resets) is sent through Resend over SMTP.

### Operations

- The container runs the queue worker and the scheduler. `generations:sync` polls every minute.
- Production needs `QUEUE_CONNECTION=database` and the `PIXELFORGE_*` variables.
- `php artisan users:promote {email}` grants admin.
- `php artisan generations:privatize-images` was a one-time move of images from the public to the private disk.

An operator account for reviewers is provided separately, without the credentials.
